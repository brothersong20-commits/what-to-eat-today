A. 도입

먼저, 우리가 뜯어볼 앱

회사·모임에서 “오늘 점심 뭐 먹지?”를 투표로 정하는 작은 웹앱입니다. 로그인 없이 이름만 적고 1·2순위를 고르면 끝.

홈식당·카페 목록, 카테고리/지역 필터, 진행 중 투표
→
투표1·2순위 선택 + 참석 여부, 마감시간, QR 공유, 룰렛
→
결과가중치 집계 순위, 참석 현황, 실시간 자동 갱신
→
관리자투표·식당·카페 만들기/수정 (인증 필요)

이 네 화면을 따라가며 “왜 이런 기술을 썼는지”를 하나씩 풀어봅니다.

A. 도입

웹앱은 두 덩어리입니다

식당 비유: 손님이 보고 주문하는 ‘홀’ = 프론트엔드. 주문을 기억하고 재료를 관리하는 ‘주방·장부’ = 백엔드. 둘이 합쳐져야 식당이 굴러갑니다.
FRONTEND

보이는 쪽 — 브라우저에서 도는 화면

버튼·목록·투표 UI. 사용자가 직접 만지는 모든 것. 이 프로젝트는 직접 손으로 작성했습니다.

BACKEND

기억하는 쪽 — 데이터 저장·규칙

누가 무엇에 투표했는지 저장하고 규칙(마감·권한)을 지킵니다. 이 프로젝트는 Supabase를 빌려 썼습니다.

바이브코딩의 핵심: 백엔드를 처음부터 짓지 말고, 잘 만들어진 걸 빌려라.

B. 이 프로젝트의 스택

왜 React를 안 썼을까?

이 앱은 React·Vue 같은 프레임워크 없이 순수 자바스크립트로 화면을 그립니다. 흔한 선택은 아니지만, 작은 앱엔 합리적입니다.

비유: 밀키트 없이 재료로 직접 요리하기. 더 자유롭지만 손이 더 갑니다.

장점

가볍다 · 의존성이 적다 · “DOM이 어떻게 도는지” 개념을 제대로 배운다 · 빌드가 단순하다

단점

화면·상태가 많아지면 직접 관리가 버겁다 → 그래서 보통은 React 같은 프레임워크를 씁니다

교훈: 프레임워크는 “규모가 커질 때” 필요한 도구. 작으면 없어도 됩니다.

B. 이 프로젝트의 스택

SPA & 해시 라우터

  • SPA(싱글 페이지 앱) — 페이지 전체를 새로고침하지 않고, 한 페이지 안에서 화면만 갈아끼움 → 빠르고 매끄러움
  • 해시 라우터 — 주소의 # 뒤를 보고 어떤 화면을 그릴지 결정
  • 왜 해시? — 정적 호스팅에서 새로고침해도 안 깨짐. 서버 설정(SPA fallback)이 불필요
/#/                홈
/#/vote/123        123번 투표 화면
/#/result/123      123번 결과 화면
/#/admin           관리자

새 화면을 추가하려면 라우터에 경로 한 줄을 등록하면 됩니다.

B. 이 프로젝트의 스택

Supabase — 백엔드를 통째로 빌리기

비유: 주방을 직접 짓는 대신 ‘공유주방’을 임대. 설비(DB·인증·실시간)가 이미 다 갖춰져 있습니다.
  • 무엇 — Postgres 데이터베이스 + 권한 + 실시간 + 인증 + 파일 저장을 한 번에 제공
  • 이 프로젝트 — 식당·카페·투표·표 데이터를 여기에 저장. 브라우저는 공개키로만 접근
  • 핵심 원칙 — 읽기는 직접 조회, 쓰기는 함수(RPC)를 통해서만 (다음 장)

바이브코더에게 가장 가성비 좋은 백엔드 출발점입니다.

B. 이 프로젝트의 스택

왜 브라우저가 DB에 직접 못 쓰게 막았나

  • RLS (행 단위 보안) — 테이블마다 “누가 무엇을 할 수 있나” 규칙. 여기선 일반 사용자 = 읽기만 허용
  • 그럼 투표 저장은? — 서버 함수 submit_vote 같은 RPC를 호출. 함수가 검증한 뒤 대신 기록(security definer)
  • 왜 이렇게? — 브라우저 코드는 누구나 열어볼 수 있음. 직접 쓰기를 허용하면 조작 위험 → 규칙은 서버가 쥔다
  • 마감시간도 서버가 다시 검증 — 사용자 PC 시계를 믿지 않습니다
비유: 손님이 장부에 직접 못 적게 하고, 점원에게 “이거 적어주세요”라고 부탁(RPC). 점원이 규칙(마감·중복)을 확인하고 적습니다.
B. 이 프로젝트의 스택

실시간 — 남이 투표하면 내 화면이 갱신

비유: 단톡방. 누가 메시지를 보내면 모두의 화면에 즉시 뜹니다. ‘새로고침’ 버튼이 필요 없습니다.
  • 무엇 — DB가 바뀌면 연결된 모든 사람에게 즉시 알림(구독)
  • 이 프로젝트 — 결과·관리자 화면이 votes 테이블 변경을 구독 → 새 표가 들어오면 순위가 자동 갱신
  • 주의 — 화면을 떠날 때 구독을 해제(cleanup) 해야 함. 안 하면 연결이 쌓여 메모리 누수
B. 이 프로젝트의 스택

관리자 인증은 두 번 확인합니다

비유: 출입증을 보여주고(1차), 경비실에서 명단과 대조(2차). 둘 다 통과해야 입장.
  • 1차 (브라우저) — 입력한 키를 클라이언트의 설정값과 비교 → 통과 시 로컬에 저장
  • 2차 (서버) — 관리자용 RPC가 DB 안에 숨겨둔 진짜 키와 다시 대조
  • 규칙 — 두 키 값은 항상 같게 유지. 진짜 검증은 서버가 책임

교훈: 클라이언트 검증은 ‘편의’, 서버 검증이 ‘진짜 자물쇠’입니다.

C. 그럼 나는 뭘로 시작하지?

스택은 유행이 아니라 필요로 고른다

“요즘 뜨는 거”가 아니라 “이 프로젝트가 무엇을 필요로 하나”를 먼저 물으세요.

질문 1

데이터를 저장·공유?

혼자 보는 계산기면 백엔드 불필요. 여러 명이 공유하면 DB 필요.

질문 2

로그인이 필요?

이름만으로 충분한가, 진짜 계정·권한이 필요한가.

질문 3

특수 기능?

실시간·결제·AI·검색노출 — 있으면 거기에 맞는 부품을 더한다.

원칙: 작게 시작 → 필요할 때 더한다. 처음부터 전부 끼우지 마세요.

C. 추천 조합 · 레벨 1

레벨 1 — 장난감 / 정적 페이지

계산기, 랜딩 페이지, 포트폴리오, 간단 도구. 저장할 데이터가 거의 없음.

추천 조합

순수 HTML·CSS·JS  또는  Vite + Vanilla JS

호스팅: Vercel · Netlify · GitHub Pages (전부 무료 가능) — 백엔드 없음

왜: 가장 빠르게 만들고 배포하며 ‘웹의 기본기’를 배웁니다. 이 단계가 탄탄해야 다음이 쉬워요.

C. 추천 조합 · 레벨 2

레벨 2 — 데이터·공유가 필요 (← 이 프로젝트)

투표·방명록·간단 CRUD·소규모 대시보드. 데이터를 저장·공유하고, 가벼운 인증이 필요.

추천 조합

Vite(or Next.js) + Supabase + Vercel

「오늘 뭐 먹지?」가 정확히 이 단계입니다. 실시간이 필요하면 Supabase Realtime이 이미 포함.

왜: 백엔드를 직접 안 짓고 Supabase로 해결 → 바이브코더의 ‘스윗 스폿’.

C. 추천 조합 · 레벨 3

레벨 3 — 본격 서비스

사용자 계정·결제·팀·여러 페이지. 검색 노출(SEO)과 견고함이 중요.

추천 조합

Next.js(App Router) + Postgres(Supabase/Neon) + 인증(Clerk·Supabase Auth) + Tailwind + shadcn/ui + Vercel

서버 렌더링(SSR)으로 SEO 확보, 검증된 인증·결제, 빠른 UI 구축.

왜: 사람이 많아지고 돈이 오가면 ‘견고함’이 곧 비용 절감입니다.

C. 추천 스택 · 백엔드

올인원 백엔드

DB+인증+실시간+스토리지. 바이브코더 최고의 출발점.

C. 추천 스택 · 실전

바이브코더 실전 팁

  • 비밀키는 코드가 아니라 환경변수에 — 그리고 공개되는 변수(VITE_)엔 진짜 비밀을 넣지 않기
  • 마스터키는 절대 브라우저로 — service_role 류는 서버에서만
  • git으로 자주 저장 — 작은 단위로 커밋해 언제든 되돌릴 수 있게
  • AI엔 작게 시키고 직접 확인 — “한 방에 전부” 대신 작은 단위로, 결과는 눈으로 검증
  • 바퀴를 다시 만들지 말기 — 검증된 라이브러리/서비스 재사용 > 직접 구현
  • 규칙은 서버가 쥔다 — 읽기는 자유, 쓰기·검증은 서버 함수로
